# Qwen Image 2.1 在 1024×1024 解码阶段 OOM 闪退（定位 + 修复方案评估）

> 2026-10-05 ｜ 设备 Honor BKQ-AN80（SM8850 级，16 GB 机型，`MemTotal` 14.78 GB）
> 版本 v3.0.0-alpha.4 之后自建的 debug 包（`io.github.xororz.localdream.debug`）
> 模型 `qwen_image_2_1`（FP8 `dit.safetensors`，整包 13.7 GB）
> 本文是**这个崩溃的权威正文**。量化双支持的调研留在
> [`2026-10-04-qwen21-quant-variants.md`](./2026-10-04-qwen21-quant-variants.md)（其 §12 已迁入本文）。

## 1. 结论速览

1. **崩在 VAE 解码，由 lmkd 发 SIGKILL**，不是引擎 assert，不是加载阶段，不是 `te=disk` 失效。
   证据链完整（§3）。
2. **直接原因**：整帧解码要 **2.72 GB** dma-buf，而起跑时 `MemAvailable` 只有 **1.7 GB**。
3. **根因是一次性能改动 + 权重变大叠加**：`2a79df0` 把 qwen21 的 `params_backend` 从 fork 默认的
   `all=disk` 特判成 `te=disk`（`main.cpp:379-382`），于是 **DiT 的 6792.67 MB 常驻**；
   同一 commit 又把 `dit.gguf`(Q4_0, 4 GB) 换成 FP8。与「Q4 精度不够」无关。
4. **你的第一个方向成立，而且代价远小于此前记录**：`diffusion=disk` 会让 DiT 权重在
   **采样整轮结束后、解码开始前**释放（不是每步释放）。实测口径下代价是**每个请求多约 12 s
   权重重读**，收益是把 6.79 GB 还给系统 ⇒ 解码的 2.72 GB 轻松放下。改动面只有 `main.cpp` 一个
   字符串，**不 bump ABI、不需要 WSL2 重编 engine**（§5 A）。
5. **第二个方向（量化 VAE）不成立**：① HTP 的 conv 权重路径被硬断言成 F16，整数量化只有
   matmul 路径支持；② 更关键的是**峰值根本不是权重**——VAE 全部参数只有 **644.38 MB**，
   而 2.72 GB 是 **f32 激活**，逐字节能对上（§5 C）。真正等效的杠杆是把 VAE 激活降到 f16
   （2.72 GB → 1.36 GB），但引擎的 VAE 图按构造就是 f32，**当前不支持**（§5 D）。
6. 最便宜的兜底仍是**让 1024² 真的分块**：两个常量（门槛 + tile）；接缝风险比原先估计的
   小（混合是 `smootherstep` 而非线性淡出，§5 B）。
7. **本文同时纠正 2026-10-04 那份文档的 §5.3**：那里写「`disk` 每步都释放、每步重读 ⇒ 慢到
   不可用」，是**代码层误判**（没看到 DiT 的 `compute` 显式传了 `auto_runner_end = false`）。
   勘误见 §6。

## 4. 为什么没被引擎自己的兜底救回来

1. **1024² 根本不进分块**：`PipelineDit.hpp:194-197` 只在 `w*h > kTileAbovePixels` 时才把
   `vae_tile_size` 传给引擎，而 `kTileAbovePixels = 1536L*1536L`（`PipelineDit.hpp:285`）。
2. **就算传了也不切**：`vae_tile_size` 的单位是**潜空间**；`sd_tiling_calc_tiles()`
   （`src/runtime/tiling.cpp:11-58`）在 `small_dim <= tile_size` 时判 1 块，而 `main.cpp:98`
   默认 `dit_vae_tile_size = 64` 正好等于 1024² 的 latent 边长（`scale_factor = 16`）。
3. **失败的形式不是「分配返回空」**：`decode_first_stage()`
   （`src/pipeline/diffusion_engine.cpp:2624-2636`）在 `decoded.empty()` 时会调
   `backend_fit::prepare_vae_decode_retry_tiling()` 打开 `rel_size=0.5`（⇒ tile 32 latent
   ⇒ 真 2×2）重试；但本机 dma-buf 是**慢而成功**（3.85 s 拿到 1.2 GB），内核的失败反应是
   杀进程 ⇒ 兜底路径从未执行。
4. **自动驱逐在 HTP 上永远不触发**：`check_capacity()`（`src/model_manager.cpp:1580-1600`）
   要 `ggml_backend_dev_memory()` 返回非 0 才计入预算，而 Hexagon 的实现直接
   `*free = 0; *total = 0`（`ggml/src/ggml-hexagon/ggml-hexagon.cpp:7022-7027`）。
5. **mmap 在 HTP 上是死路**：`can_mmap_storage` 需要 host buffer，Hexagon 的 props 是
   `host_buffer = false, buffer_from_host_ptr = false, mmap_support = false`
   （`ggml-hexagon.cpp:7035-7050`）。所以「方案 D（补 `enable_mmap`）」这条路对本机无效，
   可以彻底划掉。
6. `dit_vae_tile_size` / `dit_threads` **没有 CLI flag**（`main.cpp` 只在 `:98` 声明、`:387`
   传参），扫参数每次都要重编 core。

## 5. 方案评估

### A. 采样整轮结束先释放 DiT 权重，再解码 —— **首选，一个字符串**

机制逐环核实如下（这就是你提的方案，引擎已经支持，只是被 qwen21 的特判关掉了）：

| 环节 | 代码 | 事实 |
|---|---|---|
| 谁来释放 | `src/pipeline/diffusion_engine.cpp:2087-2095` | `sample()` 里 RAII `RunnerEndOnExit sample_diffusion_runner_end{work_diffusion_model.get()}`，**sample() 返回时**触发 `runner_end()` |
| 时机对不对 | `src/pipeline/image.cpp:848`（`sd->sample(...)`）→ 之后才 `decode_first_stage` | 释放在**最后一个去噪步之后、解码之前**，正是需要的时机 |
| 会不会每步触发 | `src/model/diffusion/qwen_image_2_1.hpp:468` | `GGMLRunner::compute(build, n_threads, /*auto_runner_end=*/false)`；`compute()` 的 guard 只在 `auto_runner_end` 为真时结束（`src/core/ggml_runner.cpp:574-595`）⇒ **每步不释放** |
| 释放条件 | `src/model_manager.cpp:1117-1165` | 非强制释放要求 `pin_count == 0 && !staged_to_compute_backend && residency_mode == ResidencyMode::Disk`；`residency_mode` 由 `params_backend_is_disk(module)` 决定（`diffusion_engine.cpp:354-355`）⇒ **必须是 disk 模式** |
| 真的还给系统吗 | `model_manager.cpp:1096-1114` → `ggml_backend_buffer_free` → `ggml-hexagon.cpp:718-722` → `rpcmem_free`（`:554/:562`） | dma-buf 被真正释放，不是搬到别处 |
| 顺带还释放什么 | `ggml_runner.cpp:473-474` | `runner_end()` 先 `workspace_.release()` + `cache_.clear()` ⇒ 那 166 s 里**不新增也不释放**的常驻激活/workspace 一起回收，所以实际归还量 **≥ 6.79 GB** |
| 重读代价 | `model_manager.cpp:423`、`:436` | `load_tensors_to_params_backend` 只处理 `loaded_to_params_backend == false` 的张量 ⇒ **每轮一次**，不是每步（入口 `prepare_params` 在 `:1397`） |

改动：`app/src/main/cpp/src/main.cpp:379-382`

```cpp
// 现在（2a79df0 引入的性能特判）
opts.type == ServerOptions::ModelType::kQwenImage21 ? "te=disk" : opts.dit_params_backend
// 方案 A
... ? "te=disk,diffusion=disk" : opts.dit_params_backend
```

代价与收益（实测口径）：

- 收益：解码开始前 `avail` 从约 1.7 GB 抬到约 **1.7 + 6.79 ≈ 8.5 GB**（线性估算，实际还
  包含 workspace/cache），2.72 GB 峰值轻松容纳；顺带让后台 App 不再被连环杀，
  请求之间也不再长期占着 DiT 的 6.79 GB（TE 那 5.18 GB 现在就已经释放了）。
- 代价：每个请求多一次 `dit.safetensors` 载入。本机实测 `copy_to_backend` **11.85 s**
  （整个 loading 13.81 s）；对 166 s 的 20 步运行约 **+7 %**。
  `batch_count > 1` 时 `sample()` 每张返回都会释放 ⇒ 每张多约 12 s。
- 这**就是 `2a79df0` 之前 fork 的默认行为**（`dit_params_backend` 默认 `all=disk`，
  `main.cpp:96`；zimage/klein 至今仍走默认），当时 Q4 权重能出图。也就是说这条路径在本仓库
  有先例，不是新造的野路子。
- 风险：`disk` 与 mmap 互斥（§4.5）但本机本来就用不了 mmap，无额外损失；权重每轮重读走 UFS，
  发热/功耗略增。
- 覆盖面：A 只把内存还给**解码**。参考图 / init latent 的 VAE **encode**发生在采样之前，
  而 DiT 是**首次去噪步才懒加载**（本次日志顺序可证：conditioning 在 7.87 s、TE 释放，
  `loading tensors completed` 在 23.83 s ⇒ DiT 在 encode 之后才建起来），所以前置 encode
  本来就不与 DiT 常驻争抢；A 之后连第二个请求的 encode 也更宽松（上一轮的权重已经释放掉）。
- 也就是说 A 的作用面正好是本次崩溃的那一段，没有明显的边角遗漏。

验证（改动后只需重编 core，**不 bump ABI、不动 engine**）：
1. `rebuild-native.bat` 或 `cpp/build.sh`（后者会自动写 `core.json`；走手动 cmake 要按
   AGENTS.md 补写 manifest）；
2. `./build-sm8850.sh debug basic` + `adb install -r`；
3. 同一条长提示词、20 步、1024×1024：看日志里**是否出现第二条**
   `released params backend buffers (… from HTP0`（在 `sampling completed` 之后、
   `num tiles`/解码之前），以及 `avail` 是否在解码前跳回 ~8 G；
4. 记录墙钟：`loading tensors completed` 是否变成**每张一次**、多花多少秒。

### B. 让 1024² 真的分块 —— 最便宜的兜底（接缝风险比预想小）

两个常量：`kTileAbovePixels`（`PipelineDit.hpp:285`）降到 1024² 以下，`dit_vae_tile_size`
（`main.cpp:98`）从 64 改成 **32**（⇒ 2×2）或 16（⇒ 4×4）。tile 32 时单块是 512×512 像素，
§2 里那三笔按面积线性缩小到约 **1/4**（≈0.68 GB）。

风险：**接缝比原先估计的更温和**。混合不是线性淡出，而是 `smootherstep`
（`6x⁵−15x⁴+10x³`，定义在 `src/runtime/tiling.cpp:110-113`，混合在 `:123-133`）——
两端导数为 0，所以渐变带内是平滑过渡而不是折角。`tile_overlap = 0.25` 仍是 25 % 的过渡带宽度
（`PipelineDit.hpp:197` 写死 0.25f），需要人眼验收天空/皮肤这类平滑渐变。

建议与 A 放在**同一次重编**里做，并顺手把 `--dit-vae-tile-size` / `--dit-vae-tile-above` /
`--dit-threads` 做成 CLI flag（§4.6），之后扫参数不再需要重编。

### C. 量化 VAE 权重 —— **不成立**

- **HTP 的 conv 路径不接受整数量化权重**：`ggml-hexagon.cpp:1552-1560` 对
  `USAGE_WEIGHTS + GGML_HEXAGON_TENSOR_CONV2D` 直接
  `GGML_ASSERT(tensor->type == GGML_TYPE_F16)`；`ggml_hexagon_is_conv2d_hmx_weight()`
  （`:1405-1411`）同样要求 `F16`。整数量化（`q4_0/q8_0/iq4_nl/mxfp4/f8_e4m3`，`:255-259`）
  只在 **HMX matmul** 权重路径受支持（`ggml_hexagon_is_hmx_weight_type`，`:261-263`）。
- 加载侧其实**允许**（`model_loader.cpp:774-797` 的 `tensor_type_rules` 接受任意类型名，
  `tensor_should_be_converted()` `:1489-1524` 的排除表里没有 VAE 张量），所以「能不能塞进去」
  和「HTP 能不能跑」是两件事——真塞进去会在 set-tensor 时 assert，或退回 HVX 反量化路径，
  而 `dit/stable-diffusion.cpp.patch` 自己就警告退回路径**结果不正确**。
- 更根本的是**账不对**：VAE 全部参数 644.38 MB，峰值 2.72 GB 是 f32 激活（§2）。就算权重
  砍一半也只省约 320 MB，且**一点也没动到激活**。

### D. 把 VAE 激活从 f32 降到 f16 —— 真正的杠杆，但当前不支持

这是唯一能直接砍掉约一半峰值（2.72 → 1.36 GB）的选项，但引擎做不到：
`VAE::_compute` 的签名就是 `sd::Tensor<float>`（`src/model/vae/vae.hpp:15-17`），
`make_input` 由 `sd::Tensor<T>` 建图张量（`src/core/ggml_runner.h:285-290`），
`WanVAERunner::build_graph` 整个解码是**一张单体图**（`wan_vae.hpp:1463-1473`）。
文件里的 `bf16: 238` 只是**磁盘上的权重类型统计**（`model_loader.cpp:717-736` 读
`tensor_storage.type`），HTP 还会把 bf16 权重转成 f16（`ggml_hexagon.cpp:266`
`ggml_hexagon_hmx_weight_storage_type`，应用于 `:1569-1572`）—— 权重侧省不到激活。
要做是 fork 级改动（穿透 `sd::Tensor<float>` 边界 + CPU 回读路径），不建议为这个 OOM 开刀。

### E. `vae=cpu` —— 字符串级，但峰值只是换个地方

`sd_parse_backend_assignment()`（`ggml_extend_backend.cpp:596`）支持
`vae|firststage|autoencoder|tae` 模块名（`:70-72`），所以 `diffusion=HTP0,vae=cpu`
是配置不是代码。但 2.72 GB 会从 dma-buf 变成进程普通 RAM，**仍然在同一片 14.78 GB 里**，
且这次要计入 RSS 记账（lmkd 对 RSS 更敏感，未必更划算）；而 Wan 的 3D conv + 39 个
`feat_cache`（`wan_vae.hpp:1057-1075`）在 CPU 上从没测过，大概率是分钟级。
MNN 只覆盖 `sd15cpu`/`sdxlmnn`（`main.cpp:103` 的 `isMnn()`），救不了这条。

### F. 降分辨率对照 —— 零成本，进行中

DiT 尺寸按 64 px 步进（`DitResolution.kt:11-19`，512–2048），896/960 都可直接拖。
线性折算（解码峰值 ∝ 面积，起跑 `avail` ≈1.7 GB）：

| 分辨率 | latent（`scale_factor=16`） | 相对 1024² | 预测解码峰值 | 判定 |
|---|---|---|---|---|
| 1024×1024 | 64×64 | 1.000 | 2.72 GB（**实测**） | 长提示词崩 / 短提示词过 |
| 960×960 | 60×60 | 0.879 | ≈2.39 GB | 预测仍偏紧 |
| 896×896 | 56×56 | 0.766 | ≈2.08 GB | 预测临界 |
| 832×832 | 52×52 | 0.660 | ≈1.80 GB | 预测应过 |
| 768×768 | 48×48 | 0.563 | ≈1.53 GB | 预测稳过 |

> 这是**预测**不是保证：`avail` 会被 lmkd 回收后台而抬高，dma-buf 还受 CMA/碎片影响
> （崩前 `cma_free` 只剩约 24 MB）。实验真正的产出是「最大能过的面积」这个实测数——
> 它决定 §5 B 该选多大的 tile。判读口径在 §7 第 1 步。

固定同一条长提示词、20 步、同 seed，只改分辨率；两次之间等机身降温（崩时有
`temperature control state 1`，别把降频当成 OOM）。

## 6. 勘误（对本仓库另一篇文档）

`docs/2026-10-04-qwen21-quant-variants.md`：

1. **§5.3「`disk` 每次 `runner_end()` 就丢，DiT 每步都跑一次 `runner_end()` ⇒ `all=disk`
   会把 8 GB 权重每步重读一遍 ⇒ 慢到不可用」是错的**，方案 C 的否定理由因此不成立。
   错因：只看 `ggml_runner.h:318` 的默认值 `auto_runner_end = true` 就推断「每步都结束」，
   没看实际调用点 `qwen_image_2_1.hpp:468` 显式传了 `false`；`sample()` 用 RAII 在**整轮**
   结束时才调 `runner_end()`（`diffusion_engine.cpp:2087-2095`）。真实代价是
   **每请求一次重读 ≈12 s**，即 §5 A。
2. 因此该文档 §1 第 4/5 点、§6 表、§7 方案 C 那一行、§10.3 判读表里「只有 `te=disk`→
   `all=disk`（慢）」的括注都应读作「代价约 12 s/请求」，不再是「不可用」。
3. 该文档 §12（崩溃实测）已整体迁入本文 §2–§4；那边保留一行指针。

> 方案 C 当时**从未在真机量化过**（只编过 core 就 revert 了），所以 §5 A 的「+12 s」目前
> 是**由 17:30 那次 `copy_to_backend 11.85 s` 折算**的预期，不是实测。落地时按 §5 A 的
> 验证步骤补实测数字。
